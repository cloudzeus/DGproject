# Customer portal: dashboard, notifications, MoM, files, timeline

Ημερομηνία: 2026-07-30
Κατάσταση: εγκεκριμένο, υπό υλοποίηση

## Το πρόβλημα

Το `/portal` απαντά στο «σε τι κατάσταση είναι τα έργα μου;» — τέσσερα stat tiles
και ένα grid έργων. Δεν απαντά στο ερώτημα για το οποίο ανοίγει κανείς ένα portal:
**«τι άλλαξε από την τελευταία φορά, και τι περιμένει εμένα;»**

Δύο δεδομένα του κώδικα καθορίζουν τον σχεδιασμό:

1. Το `Notification` model **υπάρχει ήδη** (`lib/notifications.ts`, καμπανάκι στο
   `components/layout/topbar.tsx`) αλλά **κάθε** σημείο εκπομπής ειδοποιεί μόνο
   προσωπικό. Πελάτης δεν έχει λάβει ποτέ ειδοποίηση. Άρα το κενό είναι στο
   emit layer, όχι στο UI.
2. Η ορατότητα είναι ήδη fail-closed (`taskVisibilityFilter`,
   `attachmentVisibilityFilter`, `commentVisibilityFilter`, `getPortalScope`).
   Κάθε νέα επιφάνεια περνά από αυτά, αλλιώς γίνεται αυτή το σημείο διαρροής.

## Αρχιτεκτονική απόφαση: η ροή ειδοποιήσεων ΕΙΝΑΙ το feed

Το activity timeline δεν διαβάζει τα πηγαία tables (`Task`, `Attachment`,
`Comment`, `TicketMessage`). Διαβάζει τη ροή ειδοποιήσεων.

Λόγος: τέσσερα νέα φίλτρα ορατότητας σε read path σημαίνει τέσσερα σημεία όπου
μπορεί να ζήσει bug διαρροής. Με μία εκπομπή και δύο επιφάνειες απόδοσης
(καμπανάκι + timeline), ο έλεγχος ορατότητας γίνεται **μία φορά, στην εκπομπή**.

Το `Activity` model δεν χρησιμοποιείται καθόλου εδώ: δεν έχει στήλη ορατότητας,
οπότε καταγράφει και εσωτερικά συμβάντα αδιακρίτως.

Κόστος: το feed ξεκινά άδειο την ημέρα που ανεβαίνει. Αποδεκτό.

## 1. Emit layer — `lib/notifications/customer.ts`

```
notifyProjectCustomers(projectId, { title, message, type, link })
  → project.primaryCompanyId → company.users[] → createNotifications()
  → no-op όταν isInternal, χωρίς primaryCompany, ή χωρίς customer users
```

Σημεία σύνδεσης. Κάθε ένα με πύλη ορατότητας — **εσωτερική εργασία, σχόλιο ή
αρχείο δεν παράγει ποτέ ειδοποίηση πελάτη**:

| Συμβάν | Πύλη | Τύπος |
|---|---|---|
| Εργασία → `done` | `visibility === 'shared'` | `status_change` |
| Ανέβηκε αρχείο | `visibility === 'shared'` | `comment` |
| Νέο σχόλιο | `visibility === 'shared'` | `comment` |
| Απάντηση/αλλαγή σε αίτημα | reporter email ∈ company emails | `ticket` |
| Δημοσίευση πρακτικών | `momVisibility === 'shared'` | `meeting` |

## 2. MoM — διατήρηση του υπάρχοντος μηχανισμού επιλογής

Το `mom-panel.tsx` έχει ήδη checkboxes ανά στοιχείο σε κάθε ενότητα (σύνοψη,
αποφάσεις, action items, ρίσκα, ανοιχτά ερωτήματα), με tri-state στις κεφαλίδες.
Η ομάδα ήδη επιλέγει τι μπαίνει στα πρακτικά.

Αυτή η επιλογή σήμερα **πετιέται**: ζει σε `useMemo`, στέλνεται ως `include` στο
`POST /api/meetings/[id]/send-mom`, φτιάχνει ένα email, και χάνεται.

Ο σχεδιασμός δεν εισάγει νέα έννοια έγκρισης. **Διατηρεί την υπάρχουσα** — τα
ίδια checkboxes, δύο προορισμοί: το email και το portal.

```prisma
enum MomVisibility {
  internal   // default — έξοδος LLM δεν φτάνει ποτέ αφιλτράριστη στον πελάτη
  shared
}

model MeetingNote {
  momVisibility    MomVisibility @default(internal)
  momSharedInclude Json?         // παγωμένο MomIncludeFilter — τι τσεκαρίστηκε
  momSharedById    String?
  momSharedAt      DateTime?
}
```

Το portal αποδίδει μέσω του **ίδιου** `applyFilter()` του `lib/meeting-mom.ts`,
διαβάζοντας το `momSharedInclude`. Ό,τι δεν τσεκαρίστηκε δεν φεύγει από τον server.

Πύλη ανάγνωσης, διπλή και fail-closed και στα δύο σκέλη:
`projectId ∈ scope.projectIds` **ΚΑΙ** `momVisibility === 'shared'`.

### Δύο αποφάσεις

**Η αποστολή email δεν δημοσιεύει στο portal.** Νέο κουμπί «Δημοσίευση στο
portal» στο `mom-panel.tsx`, προσυμπληρωμένο με ό,τι είναι ήδη τσεκαρισμένο.
Λόγος: το να στείλεις email σε έναν άνθρωπο δεν είναι το ίδιο με το να
δημοσιεύσεις σε portal που παραμένει και είναι αναγνώσιμο από όλη την εταιρία για
πάντα. Το `lib/portal/scope.ts` δηλώνει ότι το φίλτρο ανάγνωσης είναι πάντα
fail-closed· η σιωπηρή δημοσίευση θα ήταν η μία εξαίρεση.

**Τα ρίσκα ξεκινούν ξετσέκαρα για το portal.** Η ενότητα ρίσκων αφορά συχνά τον
ίδιο τον πελάτη («καθυστερεί τις εγκρίσεις», «ασαφές scope»). Επειδή το φίλτρο
είναι ούτως ή άλλως ανά στοιχείο, αυτό είναι μόνο default: η δημοσίευση
προσυμπληρώνει `riskIndexes: []` ενώ σύνοψη/αποφάσεις/actions/ερωτήματα
μεταφέρονται όπως είναι. Η ομάδα μπορεί να τα τσεκάρει ρητά.

## 3. Επιφάνειες portal

| Διαδρομή | Περιεχόμενο |
|---|---|
| `/portal` | ανασχεδιασμένο dashboard (κάτω) |
| `/portal/notifications` | πλήρες ιστορικό, φίλτρο ανά τύπο |
| `/portal/meetings` | δημοσιευμένα πρακτικά όλων των έργων |
| `/portal/meetings/[id]` | πλήρη πρακτικά από το αποθηκευμένο φίλτρο |
| `/portal/files` | κοινόχρηστα αρχεία όλων των έργων, με αναζήτηση |
| `/portal/timeline` | προθεσμίες και ορόσημα |

Το `portal-project-tabs.tsx` αποκτά tab **Συσκέψεις** (σήμερα: Επισκόπηση,
Εργασίες, Ομάδα, Αρχεία).

## 4. Διάταξη dashboard

Προάγει τη **δράση** πάνω από την **κατάσταση**. Σήμερα το «χρειάζονται εσάς»
είναι θαμμένο κάτω από τέσσερα tiles που ο πελάτης έχει ήδη διαβάσει.

```
┌─ header ─────────────────────────────── 🔔³ ─ avatar ─ έξοδος ─┐
│  Πύλη πελατών                                                  │
│  ΟΝΟΜΑ ΕΤΑΙΡΙΑΣ · 3 ενεργά έργα · 47 εργασίες                  │
├────────────────────────────────────────────────────────────────┤
│  ⚡ ΧΡΕΙΑΖΟΝΤΑΙ ΕΣΑΣ                                           │
├────────────────────────────────────────────────────────────────┤
│  [Ολοκλήρωση] [Σε εξέλιξη] [Αιτήματα] [Ορόσημα]                │
├──────────────────────────────────┬─────────────────────────────┤
│  ΕΡΓΑ ΣΕ ΕΞΕΛΙΞΗ                 │  ΕΠΟΜΕΝΑ ΟΡΟΣΗΜΑ            │
│  (grid καρτών)                   │  ΠΡΟΣΦΑΤΗ ΔΡΑΣΤΗΡΙΟΤΗΤΑ     │
│                                  │  ΠΡΟΣΦΑΤΑ ΠΡΑΚΤΙΚΑ          │
│                                  │  ΠΡΟΣΦΑΤΑ ΑΡΧΕΙΑ            │
└──────────────────────────────────┴─────────────────────────────┘
```

Η δεξιά στήλη είναι `sticky` σε `lg:` και στοιβάζεται κάτω από το grid σε mobile.
Το καμπανάκι μπαίνει στο header, όχι στο nav, ώστε ο αριθμός αδιάβαστων να
φαίνεται από κάθε σελίδα.

Οπτική γλώσσα αμετάβλητη: `fluent-neutral-*` για μελάνι, `shadow-fluent-2/8`
δύο στρώσεων, 8px radius σε κάρτες, `bg-acrylic` header, πορτοκαλί μόνο για
προσοχή. Κανένα νέο χρώμα.

## 5. Migration

Μία migration καλύπτει το `MomVisibility`, τις τέσσερις στήλες του `MeetingNote`
και την τιμή `meeting` στο `NotificationType`.

Παράγεται με `prisma migrate diff` (το shadow DB είναι σπασμένο) και **αφαιρούνται
οι γραμμές `DROP INDEX`** ώστε να επιβιώσουν τα FULLTEXT indexes — αλλιώς σπάει
σιωπηλά το ticket triage.
